## Форма: фактический контракт

Форма полностью работает как интерфейс, но заявки ещё не принимаются. Данных в БД, localStorage, email или Telegram сейчас нет. Endpoint не читает тело запроса и возвращает:

```http
HTTP/1.1 503 Service Unavailable
Cache-Control: no-store
Retry-After: 3600
```

```json
{"saved":false,"code":"LEADS_NOT_CONFIGURED"}
```

Клиент отправляет JSON на `POST /api/leads` с `Content-Type: application/json`. Таймаут — 15 секунд.

```json
{
  "full_name": "Тестовый пользователь",
  "phone": "+79679804740",
  "message": "Нужен бот для сбора заявок",
  "privacy_consent": true,
  "website": ""
}
```

Номер выше иллюстрирует формат; тестовые записи в рабочей БД создавать с явно согласованными тестовыми данными.

| Поле | Текущая валидация |
| --- | --- |
| `full_name` | trim, 2–120 символов |
| `phone` | Требуется `+` и код страны; допускаются пробелы, скобки, точки и дефисы при вводе. После нормализации `+` и 7–15 цифр; первая цифра не 0 |
| `message` | Обязательно, trim, 10–2000 символов |
| `privacy_consent` | Boolean, только true |
| `website` | Honeypot, только пустая строка |

Форма имеет noValidate: клиентскую проверку выполняет Zod, ошибки привязаны к полям, фокус переводится на первое ошибочное поле. Статусы: idle, sending, success, error. Повторы блокируются ref-lock и disabled-кнопкой только пока выполняется один запрос. При ошибке введённые значения остаются в DOM формы; это не сохранение в БД. После перезагрузки они не восстанавливаются.

Успех показывается только при успешном HTTP-статусе и JSON с `saved: true` и непустым строковым `id`:

```json
{"saved":true,"id":"UUID-сохранённой-заявки"}
```

HTTP 201 совместим с текущим клиентом. Просто HTTP 200, `{ok:true}` или отсутствие id приводят к ошибке. Возвращать success можно после подтверждённого сохранения. После успеха форма заменяется подтверждением, на него переносится фокус.

Клиент пока не отображает серверные ошибки отдельных полей или отдельные сообщения 429: все неуспешные ответы показывают общее сообщение. Если нужно добавить это, согласовать формат ошибок и доработать адаптер, сохранив подписи, доступность и размеры UI.

## Backend и БД: согласованное направление из PROJECT_BRIEF

Один серверный обработчик в Next.js и PostgreSQL через Supabase. Использовать уже существующий Route Handler, а не добавлять параллельно Server Action с дублированием бизнес-логики. SDK Supabase и миграции пока отсутствуют.

Минимальная таблица из брифа — `leads`:

| Поле | Тип / требование |
| --- | --- |
| `id` | uuid primary key, генерируется сервером/БД |
| `full_name` | text, обязательное, с ограничениями длины |
| `phone` | text, нормализованный международный номер |
| `message` | text, обязательное согласно текущему продуктовому решению |
| `status` | text, default new; CHECK: new / in_progress / closed |
| `consent_at` | timestamptz, серверное время принятого согласия |
| `created_at` | timestamptz, серверное время создания |

Нужно разработать воспроизводимые SQL-миграции, ограничения и RLS. Публичные anon/authenticated посетители не должны читать, перечислять или менять заявки. Запись — через доверенный сервер с минимально необходимыми правами. Сервисный ключ с обходом RLS требует отдельной серверной изоляции; сама включённая RLS не защищает от утечки такого ключа.

IP и данные аналитики не входят в согласованную таблицу. Если нужен IP для rate limiting, определить источник за доверенным proxy, срок технического использования и не переносить его автоматически в заявки. Поля вроде версии политики, idempotency key и статуса уведомления — предложения следующего этапа, ещё не реализованы.

## Порядок реализации следующего этапа

1. Проверить актуальную рабочую копию и бриф. Уточнить Supabase/hosting, регион данных, операторские сведения, хранение/удаление, нужны ли уведомления. Для подключения получить секреты безопасным способом, не через публичный код или коммиты.
2. Создать миграцию leads, ограничения и политики доступа. Подключить серверный модуль БД. Секретные env не имеют префикса NEXT_PUBLIC_; в .env.example только названия и пустые значения.
3. В Route Handler ограничить размер тела, проверить Content-Type/JSON, повторно применить leadSchema. Клиентская проверка не является защитой endpoint. Для same-origin формы определить проверку Origin/Host с учётом реального hosting, не отражать произвольные origins в CORS.
4. Добавить honeypot, серверное ограничение частоты с общим хранилищем для нескольких инстансов и безопасные ошибки без персональных данных. CAPTCHA — только при необходимости, она не выбрана.
5. Обеспечить ровно одну запись при повторе после таймаута, сетевого сбоя и параллельных запросах. Текущий frontend-lock не решает серверную идемпотентность. Практичный вариант для согласования: ключ на попытку, уникальное ограничение БД, возврат того же id при повторе; клиент повторно использует ключ до подтверждения. Не делать телефон уникальным: один клиент может оставить разные задачи.
6. Сначала подтвердить insert/транзакцию, затем вернуть saved/id. Ошибка БД не должна превращаться в успешный ответ. Предлагаемые статусы: 400/422 для невалидных данных, 413 для размера, 415 для Content-Type, 429 с Retry-After для лимита, 5xx при недоступности. Это целевой контракт, пока существует только заглушка 503.
7. Если владелец подтвердит уведомления, запускать их после сохранения. Сбой уведомления не должен удалять заявку или провоцировать новую запись при повторе. Для надёжности согласовать очередь/outbox и повторные попытки. Не писать телефон и текст заявки в общедоступные логи.
8. Заменить готовящийся документ /privacy согласованной политикой, определить серверную фиксацию согласия и процедуру удаления. Удалённая подпись под кнопкой не означает, что политика утверждена.
9. Выполнить интеграционные проверки на отдельной тестовой БД, затем frontend-регрессию и проверку production-конфигурации. Открытие индексации и публичный запуск — отдельный явный шаг после готовности инфраструктуры.
