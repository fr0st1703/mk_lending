# Backend и эксплуатация

Обновлено 18 октября 2026. Исходный frontend сохранён. По новому запросу владельца реализована своя админ-панель; прежние предложения Supabase из BACKEND_HANDOFF.md больше не описывают фактический backend.

## Локальная работа

Node.js 24+. `npm ci`, один раз `npm run admin:setup`, затем `npm run dev`. Панель: http://127.0.0.1:3000/admin. Случайный пароль находится в `data/admin-access.txt`, хеш — в `.env.local`. Перенесите пароль в менеджер паролей и удалите текстовый файл. Секреты, SQLite и её WAL/SHM не коммитятся.

Форма включается настройкой `LEADS_ENABLED=true`; setup устанавливает её только при отсутствии значения. Если `.env.local` уже содержит false, измените его явно. При ошибке базы API возвращает 503 без подтверждения сохранения. Заявки не пересылаются в мессенджеры или на почту.

SQLite выбрана для одного небольшого сайта и одного постоянного сервера. База реальная, не мок. Таблицы создаются в транзакции при первом запуске; версия схемы записывается в schema_migrations (версия 1). Изменение существующей схемы в будущем потребует новой миграции, а не только правки CREATE TABLE. WAL и busy timeout допускают конкурентные подключения к одному локальному диску. RLS здесь нет: БД изолируется серверным кодом, правами ОС и отсутствием публичного файлового доступа. Для нескольких серверов или serverless потребуется переход на PostgreSQL и общий лимитер/хранилище сессий.

## Панель и защита

- `/admin`: вход, заявки, статусы new / in_progress / closed, поиск без учёта регистра кириллицы, страницы по 25 записей, ручное удаление.
- `/api/admin/export`: все доступные заявки в настоящем XLSX, независимо от текущего фильтра; даты в UTC, в панели — московское время. Пользовательские поля записываются строками. Экспорт доступен только по действующей сессии, ответы не кэшируются.
- Случайная серверная сессия хранится в БД только в виде SHA-256. Срок 8 часов. Cookie HttpOnly/SameSite=Strict, Secure при HTTPS. Выход отзывает сессию.
- Пароль хранится в виде scrypt-хеша с солью. Для смены на Windows остановите сервер и выполните `npm run admin:password`: дважды введите свой пароль (12–256 символов, скрытый ввод). Команда сохраняет только новый хеш, завершает старые сессии и удаляет файл первоначального пароля. Затем запустите сервер снова. Другие настройки и заявки сохраняются. Не передавайте пароль в чат или аргументах команд.
- Все изменяющие запросы проверяют Origin по APP_ORIGIN, SQL использует параметры. JSON читается потоком с лимитом 16 KB (вход 2 KB, статус 1 KB).
- Лимиты в общей SQLite: заявки 30 / 10 минут; вход 10 / 15 минут; просмотры 120 / минуту. Без доверенного прокси лимит общий для всех запросов, это локальная конфигурация. В production прокси должен перезаписывать x-real-ip, Node доступен только прокси, затем выставляется TRUST_PROXY=true. Заголовки от произвольного клиента доверенными не считаются.
- Ключ повторной отправки хранится до удаления заявки. Клиент держит ключ и исходную нормализованную нагрузку в памяти до подтверждения. Повтор после таймаута в этой вкладке сохраняет одну запись, параллельные запросы также не создают дублей. Перезагрузка вкладки сбрасывает ключ; одинаковые заявки после перезагрузки могут создать новые записи.
- Персональные данные и пароли не выводятся приложением в логи. Веб-сервер и хостинг нужно настроить отдельно.

## Хранение и резервные копии

Владелец указал два календарных месяца. Просроченные записи исключаются из выборок панели/Excel немедленно и удаляются при обращении к сервисам, при запуске и ежечасно в работающем Node-процессе. На сервере дополнительно назначьте ежечасное внешнее задание `npm run db:cleanup` с тем же DATABASE_PATH и рабочей папкой проекта. Это необходимо и при остановленном веб-приложении. Настройка внешнего планировщика пока не выполнена: сервера нет.

Держите базу за пределами public и каталога артефактов сборки, на постоянном локальном диске. Ограничьте доступ к папке и файлам учётной записью приложения; на Windows проверьте ACL. Не используйте общедоступную сетевую папку. Не удаляйте WAL во время работы приложения.

Резервные копии пока не настроены. Перед запуском настройте согласованные SQLite backup API или остановку приложения с checkpoint, затем защищённое копирование. Простое копирование только .sqlite при работающем WAL может дать неполную копию. Копии и выгрузки — тоже персональные данные: отдельный доступ, срок удаления, процедура отзыва согласия, защита диска. Старую резервную копию перед возвратом в работу очистите от просроченных и удалённых по обращению записей, чтобы не восстановить их повторно.

## Статистика и инфраструктура

Загрузки главной страницы считаются клиентским POST, без cookies/localStorage, без уникальных ID или IP в аналитике. Пользователи с отключённым JS/блокировщиком могут не учитываться, боты могут попадать в число просмотров; это базовая внутренняя оценка. В БД только час UTC и количество. Панель суммирует последние 24 часа / 7 / 30 дней с округлением начала периода вниз до часа. Агрегаты очищаются через 31 день.

У uptime и памяти источник — текущий процесс Node.js. Доступность БД проверяется настоящими запросами. Домен/SSL отображаются как не подключённые; INFRA_READY — только ручная информационная отметка после настройки, не внешний мониторинг. Проверка сертификата и доступности сайта извне пока отсутствует.

## До публичного запуска

1. Выбрать постоянный сервер и расположение базы с учётом данных граждан РФ; уточнить страну размещения, хостинг, обработчиков и возможные трансграничные передачи для аудитории СНГ.
2. Настроить домен, HTTPS и доверенный reverse proxy с закрытым прямым доступом к Node. Скрипт start слушает 127.0.0.1, что подходит для прокси на том же сервере.
3. Создать отдельный production-пароль, задать абсолютный DATABASE_PATH и права диска, резервные копии и внешний планировщик очистки. Не переносить тестовую базу и локальный текстовый файл пароля.
4. Проверить реквизиты оператора и требуемый состав публичных сведений, необходимость уведомления Роскомнадзора, порядок обращений, размещение и правила соответствующих стран СНГ. Email для обращений владелец подтвердил: m.kozlov76@yandex.ru; почтовый адрес не предоставлен. Тексты типовые и требуют проверки под фактическое размещение, договоры и процедуры.
5. Дополнить политику сведениями о хостинге/обработчиках. После проверки установить POLICY_READY=true, OPERATOR_ADDRESS, LEADS_ENABLED=true, APP_ORIGIN=https://реальный-домен. Внешний приём формы без этих условий закрыт. Этот флаг — техническая защита от случайного запуска, не юридическая проверка документа.
6. Установить NEXT_PUBLIC_SITE_URL при готовности открыть индексацию и выполнить build/start. Снять заглушку инфраструктуры INFRA_READY=true только после фактической настройки.
